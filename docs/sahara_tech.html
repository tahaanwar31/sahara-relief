Sahara Relief: niche, stack and models

Coder's Cup '26, "The Last Mile: AI on Public Rails". Technical design note for the team. Prototype on synthetic data only.

1. Niche: quarterly cash relief claims (social protection)

What we built. A multi-user public-service platform for one mock programme: a quarterly cash-relief claim (BISP-style). Three roles: Person (eligible for relief), Helper (assists many families, one at a time, with each family's own PIN as consent) and Admin (reviews uncertain cases, edits rules, runs the replay and evaluation, verifies the audit diary). Eligibility, identity, payout and registry services are mocked.

Why this niche

  • The brief's eight challenges all occur naturally here: cost-aware decisions (a wrong approval and a wrong rejection have very different costs), "I am not sure" routing, messy identity data (name variants), rule changes without redeploy, explainable decisions and an audit trail, consent with take-back, non-reader and weak-network users, and scam / forged-document detection. Most other services (licence renewal, utility bills) exercise only two or three of these.
  • Real, large, measurable need (secondary sources; verify before quoting): women's literacy about 54% vs 73% for men; about 44.7% of Pakistanis below the World Bank $4.20/day line; 10 to 12 million BISP families; 68% of women own a phone vs 93% of men, and 28% of women internet users use a borrowed phone; about 140 million people live in coverage but do not use mobile internet; agents reportedly deduct Rs 1,000 to 2,000 per payment.
  • Asymmetric stakes justify a human-in-the-loop design and make "cost of being wrong" a real parameter instead of a decoration.
  • Honest scope: one service done end to end (claim, decision, review, audit) beats five shallow ones. Alternatives considered and rejected: licence/passport renewal (low stakes, few scams), utility subsidy (single rule, little identity ambiguity), health-card enrolment (needs clinical data we cannot fake credibly).

2. Architecture

LayerDesign
ClientReact 18 + TypeScript PWA. Hand-written hash router, one API layer with a live mode and an in-browser mock mode (same contract, used by tests and demos). Offline outbox in IndexedDB with idempotent replay. RTL Urdu and English switch on every screen, 108 pre-recorded audio prompts.
ServiceFastAPI (Python 3.11+). Stateless. Each request opens a transaction, runs SET LOCAL ROLE authenticated and sets request.jwt.claims, so Postgres row-level security enforces access, not the app code. A master connection exists only in service_writes.py for engine writes (decisions, evaluation, audit helpers).
DataPostgreSQL on Supabase (Mumbai), reached through the Session pooler with a small connection pool. 27 tables, 71 RLS policies, 65 triggers, hash-chained append-only audit_log, immutable rule_sets (one active), consent receipts, helper sessions, drafts and idempotency keys.
AuthAUTH_MODE=local: bcrypt in app.local_login, HS256 token; the role is read from user_roles on every request (token claims are ignored). A Supabase-Auth mode is written but untested.
Decision engineIn-process Python: hard rules, then calibrated model, then zone routing (section 4).

4. AI and decision pipeline

Order of work for each claim: (1) hard rules, (2) facts and checks, (3) calibrated probability, (4) cost-based zone, (5) explanation and trace stored with the rule-set version and checksum. Hard rules always beat the model: no consent, invalid or expired CNIC, deceased flag, possible duplicate identity, payout over cap, payout account shared / changed in 30 days / owned by a helper, scam flag, edited document.

ComponentModel and parametersWhy
Eligibility modelLogistic regression, 21 features (household PMT score, identity band, document confidence, payout flags, etc.). Trained on 12,000 synthetic cases, C=100, max_iter=2000, isotonic calibration (cv=5), seed 20261121. Model version and probability are saved in every decision.Calibrated probabilities are required for cost thresholds; weights are printable, so any decision can answer "why".
ZonesAUTO if p ≥ 0.97 and no hard rule. The line is 1 − review_cost / wrong_approval_cost = 1 − 3/100. ASK_MORE if a specific proof is missing. Otherwise HUMAN. Auto-reject line 0.15 exists but is switched off: the system never rejects alone.Expected-cost reasoning: a wrong approval (100) costs far more than a human review (3), so the machine acts only when very sure. Admins edit costs and the line; no code change.
Identity matchingRoman/Urdu name normaliser, rapidfuzz scores, weighted sum: name .30, CNIC .30, father .20, DOB .15, district .05. Bands: SAME ≥ .95, MAYBE ≥ .82, else DIFFERENT. Never "same person" on a name alone; MAYBE shows a side-by-side table.Challenge 3 (name variants such as Muhammad / Mohammad / Muhammed).

5. Safety and compliance design

  • Row-level security on all 27 tables; the role comes from the database, never the token.
  • Separation of duties: nobody approves their own case or one they helped with; payments over Rs 20,000 need two different admins; rule versions are immutable and only one is live.
  • Consent: receipts, checked on every read, take-back cuts access at once; a helper cannot grant consent, the woman types her own PIN (local mode).
  • Audit diary: append-only, hash-chained rows, a verifier re-computes the chain; update, delete and truncate are refused by triggers.
  • Abuse limits: login 40/min per IP and 8/min per email, uploads 20/min, scam check 30/min, PIN consent 8/min; extra=forbid on inputs; idempotency keys on submits.
  • Hard flags beat any score (deceased, expired CNIC, missing consent).

6. Quality and honest gaps

  • Verified: 50 database, 159 service and 27 web tests pass; live Chrome run against the real service and database for all three roles; layout scan of 52 screens in both languages.
  • Not done or not verified: deployment (Docker untested), Supabase-Auth login mode and PIN proof in that mode, native Urdu review, verification of research figures at source, demo video and slides.
