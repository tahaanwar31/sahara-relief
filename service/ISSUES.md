# Contract issues and assumptions found by the service (P2)

1. **Extra facts variables.** The engine reads `consent.active`, `scam.flag`, `identity.duplicate` and `params.*` (cutoff, borderline_band, amount, payout_cap, second_approver_over) besides the CONTRACT list. Rules saved in the database may use ONLY the CONTRACT list (`app.fact_vars()`); the service checks that when a rule set is saved. The cutoff and borderline band are also applied by the engine itself from `params`, so a changed cutoff always takes effect even if a rule has the old number inside it (db ISSUES.md #2).
2. **Rule activation is done by the admin as themselves**, not through the master connection, so the diary names the admin (`app.activate_rule_set` checks the role). `service_writes.py` therefore has no `activate_rules`; its allow-list is in the module docstring.
3. **Helper Mode consent (fixed).** The database still lets only the subject insert a consent. So the woman types HER OWN PIN on the helper's phone: `POST /consents` with `person_id` + `subject_pin` (helper only, local login mode, 8 tries/min). The service checks the PIN, records the consent as hers (`granted_by` = the helper) and writes a diary line `consent.granted_with_pin`. Wrong PIN or a family that is not the helper's: 403. In Supabase login mode this needs a different proof (not built).
4. **Helper family list** (`GET /helper/families`): row locks hide people from a helper until a session is open, so names would be empty. The service reads the names with a narrow master function and shows them ONLY where the family's consent for that helper is active; other families get masked names (`Z*** B***`) and `cnic_last4: "****"`.
5. **Resume code lookup with no login** (`GET /drafts/resume/{code}`): the row locks forbid anonymous reads. Without a token the service returns only `{case_id, step, status, requires_login: true, draft: {}}`; with the owner's token it returns the draft. Rate-limited (20 per minute per address).
6. **Officer decisions** are stored with `zone` HUMAN (approve / reject / hold) or ASK_MORE (ask_more) because the table forbids zone AUTO for a person's choice. Reason codes for them are reused from reasons.json (`R_AUTO_APPROVED` text is used for an officer approval, `R_LIKELY_NOT_ELIGIBLE` for a rejection): reasons.json has no "officer approved/rejected" codes. Suggest adding `R_OFFICER_APPROVED` / `R_OFFICER_REJECTED`.
7. **Second approver**: the first officer's APPROVE is stored but the case stays `in_review` (database refuses `approved` until two different officers approved). The reply says `needs_second_approver: true`.
8. **`cnic_numbers` in document signals is a list of strings** (as the web app expects); objects with the format check are in `cnic_checks`. `qr.found` is `null` when OpenCV is not installed (it is not installed here).
9. **`blur_score`**: 0 = sharp, 1 = very blurry.
10. **Idempotency-Key** is stored by the database for drafts (`app.save_draft`); for `POST /cases`, `/submit` and `/officer-decision` it is kept in process memory (lost on restart).
11. **Local test database serves one connection at a time**, so the service opens short-lived connections, one at a time, with a lock (`DB_SERIALIZE=0` turns the lock off for a real Postgres). `prepare_threshold` is off for the same reason.
12. **Roles for `/rules/twin`**: admin and auditor (the contract names no role). `/mock/*` registry reads: officer and admin only, and only with the person's active consent.
13. Reason codes: the contract's `R_*` list has no code for "payment released" or "officer decision"; see 6.
